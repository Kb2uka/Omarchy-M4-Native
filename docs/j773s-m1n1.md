# J773s (Mac mini, M4 Pro) bring-up m1n1

A development m1n1 for the first recoveryOS session on the Mac mini M4 Pro
(J773s, T6040). It has not run on the mini, or on any machine. Its job is
to enter proxy mode over USB, so the mini can be driven from a host machine
and the first kernel and devicetree can be loaded.

## Base: upstream, not the Air's loader

The Air's loaders are upstream m1n1 `c9ef56f` plus T8132 GPU changes in
`kboot_gpu.c` (core mask and power tables read from the T8132 GPU), a new
`m4_power.h`, a RAM-bench watchdog option in `wdt.c`, and this repository's
`patches-m1n1/` fixes. The GPU changes check for the T8132 register window
and 8 or 10 GPU cores, so they cannot serve the 16-core T6040 GPU.

The mini starts from upstream `main` at `e4419ba8` instead. Since `c9ef56f`,
upstream has added several things the mini needs:

| Upstream commit | Why the mini needs it |
|---|---|
| `e9920b9` mcc: support t604x | The mini's ADT has `mcc,t6041` |
| `3e354a2` firmware: add newer macOS / mBoot versions | Adds `mBoot-18000.121.3` (macOS 26.5.2), the mini's system firmware |
| `ef33092` tps6598x: add spmi transport | The mini's USB-C controllers are `usbc,sn201202x,spmi` |
| `3a69c73`, `9095a5e` kboot: WFI handling on M4 | Linux is told when WFI loses state |

T6040 identity (`d3699d53`) and `apcie,t6040` PCIe (`0f221fc7`) were already
present before `c9ef56f`. Upstream is now GPL-2.0 (`ce2b8a4`).

## Patches on top

| # | Patch | Source | Why it applies to J773s |
|---|---|---|---|
| 1 | dockchannel: bound the wait for TX space | this repository, `patches-m1n1/dockchannel-tx-bound.patch` | The mini's ADT has `dockchannel-uart`. The patch is not specific to any SoC: it only bounds a wait that could otherwise never end ([details](j713-m1n1-dockchannel-tx.md)) |
| 2 | dapf: gate DAPF init per SoC on the M4 generation | [damsleth/wallace](https://github.com/damsleth/wallace) RFC 3/9, unchanged | On T6040, initializing some DAPF instances raises an async L2C SError at kboot handoff (J614s). The patch runs only `dart-mtp` on T6040. The mini has no `dart-mtp`, so all of them are skipped there |
| 3 | kboot: guard stage 2 log buffer at top of RAM | wallace RFC 8/9, unchanged | On T6040, wrapping a ring buffer placed in the last physical page raises a delayed SError |
| 4 | cpu: M4: park secondaries in WFE | wallace RFC 1/9, hand-ported because upstream `smp.c` changed | Secondary cores on the M4 family lose state in WFI. They are kept in WFE |

Patches 2–4 were proven only on J614s (MacBook Pro 14-inch M4 Pro), which
has the same SoC. The authorship of each patch is kept.

Patches 2–4 are in [`patches-m1n1/j773s/`](../patches-m1n1/j773s/), and its
`series` file lists all four in order; patch 1 is the existing
`patches-m1n1/dockchannel-tx-bound.patch`.

The series is for the J773s loader only. Two of its patches also change
other SoCs, so it must not be applied to the Air's loaders as is:

- Patch 2 gates on `chip_id`. On T8132 it skips `dart-aop`, `dart-isp` and
  `dart-isp0` (the patch credits that observation to a T8132 bring-up) and
  keeps `dart-mtp` and `dart-pmp`, which the Air's keyboard and trackpad need.
  The Air's own loaders do not carry this patch.
- Patch 4 sets `broken_wfi` in upstream's shared `features_m4`, which also
  covers the M4 (T8132), M4 Max, A18 Pro, M5 and M6 cores. Every one of those
  would park its secondaries in WFE and refuse to leave WFE mode.

## Left out

- `patches-m1n1/stage1-ans-no-reset.patch`: a fix for an ANS-reset freeze
  that occurred on some J713 units (#82). It changes the behaviour of every
  M4-generation ANS and is only needed in a chainloading stage 1. Add it only
  if the mini shows the same freeze.
- The Air's T8132 GPU and RAM-bench watchdog changes, for the reasons above.
- wallace 2/9 and 4/9 (a 20 s handoff watchdog, and T6040 display carveouts
  copied from t602x). Arming the watchdog is a bring-up policy choice. Those
  carveouts assume a `disp0`/`dcp`, but the mini's ADT only has
  `dcpext0`–`dcpext2`, so its display reservations have to be worked out
  separately. That belongs with the display work.
- wallace 5/9: upstream `e9920b9` supersedes it.
- wallace 6/9 (minimal T6040 cpufreq): it reuses the t6031 cluster table,
  which the mini's 4E+4P+4P binning does not match. That is not checked, and
  upstream also has no T8132 cpufreq, so Linux handles cpufreq.
- wallace 7/9 (host tool) and 9/9 (marked RFC by its author, an incomplete
  PCIe clock prefix).

## Build

In `m4-gravity-builder:20261008` (`b2069edb8a23`; Ubuntu clang 21.1.8, rustc
1.93.1), run from the patched tree:

```sh
export PATH=/usr/lib/llvm-21/bin:$PATH M1N1_VERSION_TAG=j773s-e4419ba8-b4-20261017
make BUILDSTD=1 USE_CLANG=1 TOOLCHAIN=/usr/lib/llvm-21/bin/ LLDDIR=/usr/lib/llvm-21/bin/ -j8
```

This is a development build: no `RELEASE`, no `CHAINLOADING`, no payload. It
is installed as a raw boot object from recoveryOS, in the same form as the
Air's ([night 3 runbook](night3-runbook.md), step 6):

```sh
kmutil configure-boot -c m1n1.bin --raw --entry-point 2048 \
  --lowest-virtual-address 0 -v <target system volume>
```

The target volume is chosen at that session. Two clean builds gave the same
`build/m1n1.bin`:

```
224a373e8380a7bc0f5dff1ca209d97bbc947473f437e49eb0ee28806bc56cf5  m1n1.bin
```

The build log has six compiler warnings, all in upstream files these patches
do not touch (`dcp_iboot.c`, `tps6598x.c`, `usb.c`). The binary is kept
privately with the rest of the bring-up evidence until it is used.

## Not verified until the mini boots it

- that m1n1 reaches proxy mode on J773s and the host sees its USB device;
- the DAPF skips and the WFE parking on this board;
- which USB-C port m1n1's proxy is reachable on (see below);
- simple framebuffer handoff on HDMI. Upstream skips DCP setup on macOS 15
  and later and on boards without `dcp`, so m1n1 leaves the boot firmware's
  framebuffer in place.

## DFU port

Apple's [How to identify the DFU port on Mac](https://support.apple.com/en-us/120694)
says that on Mac mini models with Apple silicon introduced in 2025 or later,
the DFU port is the middle USB-C port when facing the back. On all other Mac
mini models with Apple silicon, it is the leftmost USB-C port when facing the
back. The M4 Pro Mac mini (Mac16,11) was introduced in 2024, so its DFU port
is the **leftmost rear USB-C port, facing the back**. The page does not name
the M4 Pro separately. That m1n1's proxy also answers on this port is
expected but untested.
